# 每日工作节奏

## 开始：从证据出发

先看 STATUS、最近一次 DELIVERIES、实际版本与新增结果。确认是否已有任务在运行、结果是否完整、是否有人留下未提交修改。先审计再决定；不要收到“已回传”就自动重跑。

向研究者用简短中文说明：**当前卡在哪、这一轮要判断什么、为什么这个判断影响研究主线。** 技术细节留在实验卡，便于追查。

## 一轮：研究者运行，AI 负责准备与审计

1. **设计**：写清假设、最简单替代解释、对照、主要指标与正确性约束。预先说明正、负、不确定三种结果各如何改变下一步。
2. **准备**：修改必要代码，完成与改动相称的本地检查；明确哪些真实设备检查尚未执行。配置、版本和结果目录可追溯。
3. **交付运行**：提供本地上传、远程运行、本地回传三组命令，明确执行位置和路径。每轮使用独立结果名，不覆盖旧结果；预计规模或时长没有依据时直接写未知。
4. **等待回传**：记录等待哪次实验、输出位置及作业归属。默认前台执行，整次运行共用一条原地刷新的进度栏，跨样本与阶段不刷出多行；详细日志独立保存；不擅自转为后台任务。不重复启动已经运行的实验。
5. **审计**：先检查完整性、错误、配置、输出长度/正确性与计量口径，再看性能。区分真实测量、模拟和代理量；保存原始证据与分析入口。
6. **决策**：继续、修正、缩小范围、暂停或进入确认。更新 STATUS，追加有用的 EVIDENCE、DECISIONS、DELIVERIES；按项目约定提交、推送，并如实报告状态。

若用户另有分工，按 PREFERENCES 执行。例如 AI 获准运行实验后可自行执行，流程仍保留相同的证据和资源边界。

## 显示维护也要验证实际体验

“有回车字符”不等于用户看到的是单条进度。涉及子进程时检查管道缓冲、日志混排、阶段结束换行与窄终端折行。可以用不加载模型的端到端预览验证显示，避免为界面修复重跑昂贵实验。非交互输出采用简洁状态记录，不堆积动画帧。

## 本地、自动检查与真实实验分别核验

新增测试依赖或外部源码时，同步维护自动检查环境的版本和目录布局。用干净检出确认测试不依赖研究者机器上偶然存在的包或未跟踪文件；推送后核对实际运行结果，不能把“本地通过”或“已推送”写成“自动检查通过”。交付中分别说明本地、自动检查、真实设备实验的状态，以及有理由跳过的测试。

不同平台可能对未承诺稳定顺序的操作给出不同合法排列。测试应按逻辑身份和真实前置条件构造状态，用替代排列验证；不能为修测试而放松运行时的安全检查。合成动作测试与真实选择质量测试分开，修好自动检查不等于完成研究正确性或性能验证。

## 控制成本

先做有区分力的小实验；形成候选后才冻结配置做独立验证。小样本用于找异常与判断是否值得继续，不能直接承诺普适效果。重复次数取决于波动与目标差异，不固定要求每次重复四次或跑完整基准。

有限诊断到达事前停止条件后，保留未解边界与原失败状态，回到仍可独立验证的主线问题。若改用记录/回放来隔离共享资源影响，先验证完整输入/响应与状态匹配；条件回放不能替代真实在线性能或修复原正确性缺口。

结果在生成时就控制体积：默认保留配置、汇总、错误、必要的逐样本记录；诊断需要完整 trace 时显式开启。压缩不等于删除；删减数据前确认仍能重建核心结论。权重、环境和大体积结果不进入常规 Git 历史。

共享机器先确认本次新增资源需求和作业归属，使用项目隔离环境；不停止他人服务、不修改公共环境。无需每轮重复检查没有变化且不影响决策的事项。

## 每轮回复保持可执行

- 这轮发现了什么，能说明什么、不能说明什么。
- 做了哪些修改，实际通过哪些检查，未验证什么。
- 下一步唯一优先动作；需要用户运行时给准确命令和输出位置。
- 当前提交/推送状态；如失败说明实际原因。

没有代码改动且不需要新实验时，不为凑流程生成同步命令。短咨询不强制产生交付文件。

## 阶段复盘与汇报

完成主要候选、发生转向或 AI 接手时，看 RESEARCH_REVIEW。每周或向导师汇报前，用“研究目标 → 已得到的证据 → 当前判断及局限 → 下周一个主要问题”组织汇报。任务完成数量不是贡献；先解决主张缺口，再扩充实验规模。
