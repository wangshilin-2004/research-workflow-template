# 持续改进与版本升级

## 两层记录

**课题层**记录发生了什么：在项目 LESSONS 中写观察、证据、改变的做法和适用边界。没有验证的经验标成建议，不立即变成规则。

**模板层**记录可迁移的方法：去掉课题、身份、设备地址、具体结果，保留“什么条件下容易误判 → 如何识别 → 最小改进 → 哪些情况不适用”。不把某课题的技术结论复制成跨领域规律。

## 何时值得更新模板

满足以下任一情况就考虑，不强求每轮更新：反复发生的交接错误；能显著减少重复劳动的做法；一项后果重要、且能说清适用边界的失败教训。单次经验可以提出候选，但应标明依据有限。

修改前问：它会改变什么实际行为？是否已有规则能覆盖？收益是否超过维护负担？尽量补一句、合并一项或删去冗余，不用每次新增表格。

每次改进说明：问题、依据类型（不放私有证据）、适用条件、改动、例外、验证方式。更新 CHANGELOG；功能或模板结构变更时更新 VERSION 与入口版本。不要为纯文字修订频繁升级版本。

## 版本规则

公开版本从 1.0.0 开始，早期内部“模板 v1/v2”对应的历史仍保留。文件级新增兼容内容升次版本；破坏现有初始化/导出约定的改变升主版本；兼容修正升补丁版本。实际升级记录以 CHANGELOG 为准。

模板的 WORKFLOW.md 与 templates/research/WORKFLOW.md 保持一致，由测试检查。新核心模板加入后，确认是否需要交接导出；新增记录优先采用可选导出，避免旧项目失效。

## 老项目升级：比较后合并

1. 保持课题已有记录完整，先查看未提交修改与当前模板版本。
2. 对比对应版本的 CHANGELOG 和所需模板；仅补入缺失且有用的文件。
3. 流程规则逐条合并。BRIEF、STATUS、EVIDENCE、DECISIONS、PREFERENCES 等真实内容绝不整份覆盖。
4. 更新项目入口的采用版本或注明局部采用。检查已有 AI 规则是否冲突。
5. 验证交接导出，记录改动并按项目约定提交。

初始化工具不是升级工具。升级不意味着重跑旧实验、补填所有空表或重新批准已授权任务。

## 公开前检查

具体课题保持独立仓库；发布模板只公开通用内容。检查待发布文件、Git 历史、附件与仓库相关公开内容，不只检查最新目录；扫描工具不能保证检测所有私人信息。凭据泄露需撤销凭据，删文件不能让历史消失。不要直接将包含真实课题历史的仓库改造成公开模板。

## 使用者反馈

可以在自己的工作流副本中维护个性化规则。向上游反馈时提交脱敏的最小例子和预期行为；无需分享课题数据。公开可见不代表第三方材料可以任意再分发，保留来源和原有许可约束。

## 执行能力的最小退出条件

新增运行尺寸或后端后，固定模式等价只是第一关；再覆盖真实混用和往返状态变化。通过后转入控制效果检验，避免无限扩展基础兼容矩阵。策略对照统一启动与预分配条件，但工作量仍按实际动作记录。
