# Research Workflow Template

**把科研目标、证据和下一步留在项目里，让不同 AI 能接着做，而不是重新猜。**

一套中文优先、与学科和 AI 产品无关的科研工作流。适合研究者主导课题、AI 辅助调研与实现、研究者运行远程实验的协作方式，也可以按项目调整分工。覆盖选题、近邻核查、基线复现、机制验证、论文写作与成果复现。

当前版本：**1.0.0** · Python **3.9+** · 工具仅依赖标准库和 Git（交接版本信息）

## 一条主线、一个当前任务、一轮可判断的实验

问题 → 近邻与基线 → 瓶颈 → 机制假设 → 最小验证 → 确认与泛化 → 贡献与论文。

每一轮只优先解决一个会改变决策的问题。正结果、负结果和不确定结果都要有下一步；不以不断运行实验、增加代码或更换算法名称代替研究进度。小实验负责探路，正式结论需要相应的对照与证据。

默认协作节奏是：**AI 设计、实现和检查 → 研究者运行 → 回传结果 → AI 审计并决定下一步**。采用这个分工不意味着把所有任务自动授权给 AI；每个项目在 PREFERENCES 中确定实际边界。

## 最小使用方法

下载本仓库后，在本仓库目录执行。目标项目必须已经存在：

```bash
python3 tools/init_project.py --project /path/to/your-project
```

它只创建 `research/` 内的记录模板；遇到已有同名文件会停止，不覆盖旧记录，也不修改已有 AI 规则。先填写 **BRIEF、PREFERENCES、STATUS** 三份文件即可，其他记录随工作产生。给项目原有 AI 入口补上一句：

> 开始工作前，请阅读 research/START_HERE.md，按当前 STATUS 接手，并遵守本项目已有规则。

AI 不能访问仓库时，可以导出一个供人工检查后传递的快照：

```bash
python3 tools/export_handoff.py --project /path/to/your-project --output /path/to/handoff-001.md
```

快照包含允许列表中的研究记录、Git 状态和文件哈希，**不包含代码和原始实验数据**。允许列表不是脱敏器：记录本身可能含有私人信息，分享前仍需核查。各 AI 的权限、工具和可访问结果不同，交接不保证无条件连续执行，也不会自动发送消息或启动实验。

## 文件各管一件事

| 记录 | 职责 |
|---|---|
| BRIEF / PREFERENCES | 研究目标、边界与协作习惯 |
| STATUS | 唯一的当前任务入口；旧任务不在这里累积 |
| IDEAS / LITERATURE | 假设、最近邻、真实阅读和复现程度 |
| EVIDENCE / DECISIONS | 可核查事实、适用范围、选择与纠正依据 |
| EXPERIMENT_TEMPLATE / ENVIRONMENT | 实验设计、执行位置、配置与结果位置 |
| DELIVERIES / HANDOFF_CHECKLIST | 实际交付、独立复核状态与接力检查 |
| RESEARCH_REVIEW / CLAIMS | 阶段方向审查、论文主张与证据缺口 |
| LESSONS | 有依据、有边界、能改变做法的经验 |

不保存 AI 的内部思维链；保存的是别人可以核查的研究判断依据。历史通过追加记录与 Git 保留，当前状态保持简洁。

## 长期使用

每个课题拥有自己的 `research/`；本仓库只维护通用流程。项目经验先记入 LESSONS，确认值得跨项目复用后，再以去掉课题信息的形式改进模板。**升级模板不会自动改写既有项目。** 具体方法见 [升级指南](docs/EVOLUTION.md) 和 [版本记录](CHANGELOG.md)。

GitHub 的 **Use this template** 会创建工作流副本；创建具体研究项目时单独选择可见性。公开模板不要求课题公开，也不应将课题资料提交回来。

## 检查与贡献

```bash
python3 -m unittest discover -s tests -v
```

改进流程时，请说明观察到的问题、适用条件、最小修改和可能增加的维护成本。优先减少重复劳动；不要为了流程完整而要求每轮填写全部文档。不要在公开 issue、提交或示例中放入未公开研究内容、个人环境或凭据。
